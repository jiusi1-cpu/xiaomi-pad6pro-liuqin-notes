# 小米平板 6 Pro 刷机 / KernelSU / 性能调优 可复用指南

> 本文把一次真实完成的完整操作整理成可迁移的流程。换机型时，把「代号、系统版本、内核 KMI、分区槽位」替换成目标设备的值即可复用，步骤与验证方法不变。

## 0. 已验证环境（本次实测基准）

| 项目 | 值 |
| --- | --- |
| 设备 | 小米平板 6 Pro |
| 型号 | `23046RP50C` |
| 代号 | `liuqin` |
| 系统 | **HyperOS `OS3.0.7.0.VMYCNXM`（Android 15）** |
| 内核 | `5.10.236-android12-9`（KMI：android12-5.10） |
| 活动槽位 | `_a` |
| Bootloader | 已解锁 |
| Root 方案 | KernelSU v3.3.1（build 32680）LKM 模式 |

**换设备要改的四处**：代号（`liuqin`）、系统版本（`OS3.0.7.0.VMYCNXM`）、内核 KMI（`android12-5.10`）、活动槽位（`_a`/`_b`）。其余步骤、命令结构和验证口径可直接套用。

## 1. 前置条件与风险

- 已解锁 Bootloader；已知晓解锁会清空数据。
- 准备好与设备 **完全匹配** 的原厂 boot 镜像和完整系统包；不同机型、不同版本的镜像严禁混用。
- 全程数据线稳定，刷写前电量充足。
- 风险：刷写 boot 失败可能无法开机；root 后部分应用（尤其游戏）可能检测并封号；本文只记录「配置是否按要求写入」，不对账号安全作保证。

## 2. 提取原厂镜像（可回退的起点）

1. 从设备当前已安装的系统分区提取官方镜像，记录提取日志。
2. 对操作过程和最终 boot 分区做 SHA-256 校验，确认拿到的是未修改的原厂镜像。
3. 保留原厂内核、原始 init 和 boot 元数据；stock boot 单独留档，作为唯一的回退材料。

对应证据：`evidence/device-extraction.json`、`evidence/boot-verification.json`。

## 3. 用 KernelSU 补丁 boot 并刷入

1. 取官方 KernelSU 发行包中与设备 KMI 一致的 LKM 资源（本例 android12 / 5.10，KernelSU v3.3.1 build 32680）。
2. 用补丁工具对原厂 boot 打补丁；不要手工替换内核镜像以外的分区。
3. 刷入补丁 boot，正常启动后验证：
   - KernelSU 管理器能识别已安装版本；
   - `ksud` 可用；
   - shell 下 UID 为 0。
4. 验证通过后才继续后面的步骤；未通过先回退 stock boot。

## 4. Root 工具链（MT 管理器 / Scene）

- MT 管理器 `bin.mt.plus` 2.26.10：经 KernelSU 授权后可读写 `/data/adb`。
- Scene `com.omarea.vtools` 9.4.11：root、CPU/GPU 监控与调度界面可用。
- 注意：冷启动压测里强制停止 Scene 会清掉它的辅助服务，需要重新绑定；日常测试不要反复强停。
- 授权后逐项截图留证：`screenshots/MT-root-verified.png`、`screenshots/Scene-root-authorized.png`。

## 5. 桌面与应用启动优化

- 做法：对桌面、系统界面、设置、文件管理器、安全中心、计算器、便签及常用工具做 ART `speed` 预编译，然后重载系统界面让编译结果生效。
- 结论：动画时长比例 `0.9` 经配对测试 **没有** 证明能减少掉帧，已恢复原厂默认 `1.0`。
- 不要部署未验证的旧版动画 hook，也不要替换系统桌面；HyperOS 当前桌面已自带动画接续逻辑，历史 hook 与新 APK 不适配。
- 实测参考：MT 冷启动 6 次中位数约 605.5 ms，speed 编译对照约 530.5 ms（样本受缓存与后台负载影响，差值不能当纯因果收益）；连续「打开 → 上滑回桌面 → 立即重开」3321 帧、74 帧未达期限、p95 10 ms、p99 15 ms。

## 6. 全局 120Hz 与后台限制（本机模块）

1. 用 Android 15 已有的显示路径设置首选显示模式，并确认重启后仍为 120Hz。
2. 把「开机后恢复显示设置 + 选定应用后台限制」做成一个 KernelSU 模块（本例 `modules/liuqin120`），开机完成后执行一次即退出，不常驻守护。
3. 脚本文件统一 UTF-8 / LF / 无 BOM——有设备上的解析器会把 `120\r` 判成非法值。
4. 后台限制按 UID 逐项设置；**共用 UID 的应用要一起处理**（本例 `com.miui.huanji` 与 `com.miui.backup` 共用 UID 6100）。
5. 重启后逐项复核，不要只看设置界面。

## 7. 游戏 120 帧：怎么测才算数

- 游戏内先设好画质与帧率档位（本例流畅画质 + 120 帧，抗锯齿关闭）。
- 用采样脚本记录实际呈现帧，而不是读设置值；指标取平均帧率、10 秒窗口区间、帧间隔中位数/p95/p99、超 16.7 ms 与超 25 ms 的次数。
- 线程分配记录主线程/渲染线程/RHI 线程落在允许的核范围（本例 4–6），不要把整个游戏锁到单核；GPU 保持按负载调频。
- 本次训练场有效采样 87.48 秒 / 10356 帧：平均 **118.37 FPS**，10 秒窗口 114.7–120.0 FPS，帧间隔中位数 8.33 ms，p95 8.39 ms，p99 16.66 ms，超 16.7 ms 共 15 次。
- 结论口径：证明「能稳定进入 120 帧档位附近」，**不能** 写成「任何场景绝对锁 120」。系统 120Hz 也不会把应用自身的 60 帧上限变成 120 帧。

## 8. 机型配置（应用级，可选）

- 方案：COPG v7.5.1 + Zygisk Next v1.5.1，配置 **只对游戏包名生效**（本例 `com.tencent.tmgp.pubgmhd`），使用目标机型 profile（红魔平板 NP05J）。
- 边界：这是应用级属性配置，不是反作弊绕过；系统全局 model 仍是本机型号，CPU 等真实信息不做整体伪装。
- 风险：游戏官方规则明确禁止 root 设备，可能带来账号、兼容性与封禁风险。

## 9. 第三方资源导入（皮肤等）

- 按 ZIP 内路径复制到游戏 `Paks` 目录，逐个做 SHA-256 比对；目标文件不存在时不算覆盖。
- 「文件已导入并校验」是事实；「游戏内视觉生效」必须目视确认后才能写进结论。
- 第三方游戏资源仅作本地留档，不要再分发。
